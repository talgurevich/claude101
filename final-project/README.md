# פרויקט הגמר — צ'אט מעל מסמכי החוג

**עבודת צוות · 2–3 ימי עבודה · הגשה: ריפו ציבורי ב-GitHub**

---

## מה בונים

ממשק צ'אט בעברית שעונה על שאלות אמיתיות של סטודנטים מתוך שני מסמכים רשמיים של המכללה — השנתון של החוג למדעי המחשב, ותקנון הלימודים לתואר ראשון.

לא chatbot כללי. מערכת שעונה **רק** ממה שכתוב במסמכים, מציינת מאיפה לקחה כל תשובה, ואומרת בפירוש "לא מופיע במסמכים" כשהתשובה לא שם.

המשפט האחרון הוא החלק הכי חשוב בפרויקט. מערכת שממציאה תשובה על תקנון גרועה בהרבה ממערכת שלא עונה בכלל.

## הסטאק המומלץ

זה המסלול שאנחנו ממליצים עליו — הוא נבדק, הוא עובד, והוא חוסך לכם החלטות שלא כדאי לשרוף עליהן זמן בפרויקט של שלושה ימים. אתם לא חייבים אותו. אם בחרתם אחרת, תכתבו משפט ב-README שמסביר למה.

**אם אתם מתלבטים — קחו את ברירת המחדל ותמשיכו הלאה.** בחירת ספריות היא לא החלק המעניין בפרויקט הזה.

|---|---|---|
| שפה | Python 3.11 ומעלה | |
| חילוץ PDF | `pdfplumber` | pip בלבד, עובד זהה ב-Mac וב-Windows |

**מה שכדאי מאוד להימנע ממנו:** embeddings, vector database, Postgres, pgvector, Chroma, torch. לא בגלל שהם כלים גרועים — בגלל שבקורפוס בגודל הזה הם תשתית מיותרת, ואחזור סמנטי בעברית הוא קרב שיאכל לכם יום שלם מתוך שלושה. אם אתם בכל זאת הולכים לשם, לכו בעיניים פקוחות ותסבירו את השיקול ב-README.

האינדקס שלכם הוא קובץ אחד בגודל כמה מאות קילובייט. זה בסדר גמור. חלק מהלמידה בפרויקט הזה היא לזהות מתי תשתית היא התשובה הלא נכונה.

## הארכיטקטורה — Agentic Retrieval

לא צנרת RAG קלאסית. במקום לשלוף top-k קטעים בכל שאלה ולקוות שפגעתם, אתם נותנים ל-Claude **כלים** על אינדקס מובנה, והוא מחליט מה לקרוא.

זה מה שאתם מממשים:

```python
def list_sections() -> list[dict]:
    """Return the table of contents: id, title, source document, page."""

def get_section(section_id: str) -> str:
    """Return the full text of one section."""

def search(query: str, limit: int = 5) -> list[dict]:
    """Lexical search over SQLite FTS5 (BM25). Returns section ids + snippets."""

def get_course_table(year: int, semester: int) -> list[dict]:
    """Return one course table as structured rows."""
```

| כלי | מה הוא מחזיר |
|---|---|
| `list_sections` | תוכן העניינים — מזהה, כותרת, מסמך מקור, עמוד |
| `get_section` | הטקסט המלא של סעיף אחד |
| `search` | חיפוש לקסיקלי, BM25 מעל FTS5 — מזהי סעיפים וקטעי הקשר |
| `get_course_table` | טבלת קורסים אחת, כשורות מובנות |

**למה ככה ולא top-k רגיל:**

- שאלות צבירה (`כמה נ"ז סה"כ בשנה ג'?`) דורשות טבלה שלמה, לא שלושה קטעים דומים סמנטית. `get_course_table` מחזיר את כולה.
- המסמכים כבר מובנים — יש להם סעיפים ממוספרים וטבלאות עם כותרות. לזרוק את המבנה הזה ולחתוך לחלונות של 1500 תווים זה להשמיד מידע שקיבלתם בחינם.
- עברית ו-embeddings זה קרב לא נעים. ככה אתם לא נכנסים אליו.

החיפוש הלקסיקלי עדיין שלכם לממש — BM25 אמיתי מעל FTS5, פשוט עטוף ככלי שהמודל קורא לו כשהוא מחליט, במקום צנרת קבועה שרצה תמיד.

## דרישות חובה

ארבע דרישות. פרויקט שלא עומד באחת מהן לא מוגש.

### 1. ציטוט מקור בכל תשובה

כל תשובה מציינת מאיזה מסמך ומאיזה סעיף/עמוד היא נלקחה. תשובה בלי מקור נחשבת תשובה שגויה, גם אם היא נכונה.

### 2. סירוב כשאין תשובה

כששאלה לא נענית מהמסמכים, התשובה היא `לא מופיע במסמכים` — ולא ניחוש, ולא ידע כללי על מכללות.

### 3. Prompt Caching

חובה. בלולאת כלים כל פנייה שולחת מחדש את כל מה שקדם לה, ובלי cache אתם משלמים על אותו טקסט שוב ושוב.

הצורה הנכונה: `cache_control` על הבלוק האחרון של כל תור. הגדרות הכלים ו-system prompt נשארים תחילית יציבה שנשמרת במטמון בין שאלות.

### 4. תקרת איטרציות

`max_iterations` בין 5 ל-8 על לולאת הכלים. סט כלים מעוצב גרוע שולח את המודל חמש-עשרה סיבובים לפני שהוא מוותר — זה מה ששורף תקציב.

בנוסף, **תדווחו ב-README כמה קריאות כלים בממוצע המערכת שלכם עושה לשאלה**. זה מדד הנדסי אמיתי, קל למדוד, וצוות שהממוצע שלו 9 יודע שיש לו בעיה בעיצוב הכלים.

## שלבי העבודה

הפרויקט מתפצל לארבעה מסלולים שרצים במקביל. שלב 1 הוא החוזה בין כולם — ברגע שיש טקסט מחולץ נקי, שאר המסלולים יכולים לעבוד עצמאית.

### יום 0 — ביחד, שעה

תקראו את שני ה-PDF-ים כבני אדם. תחליטו מה סטודנט אמיתי באמת שואל.

### שלב 1 — חילוץ ומבנה

חילוץ הטקסט, תיקון כיווניות, ניקוי תווי בקרה, זיהוי סעיפים וטבלאות, בניית אינדקס ה-FTS5.

**שער מעבר:** תפתחו את הפלט ותקראו אותו לפני שממשיכים.

### שלב 2 — שכבת המודל

הגדרת הכלים, לולאת ה-tool use, ה-system prompt, ה-caching, תקרת האיטרציות, התנהגות הסירוב.

### שלב 3 — ממשק

Streamlit, עברית ו-RTL, שאלה נכנסת ← תשובה מבוססת עם ציטוט יוצאת.

### שלב 4 — הערכה

הרצת עשר שאלות ההערכה, תיעוד הפלטים בפועל, ניתוח הכשלים.

   - הוראות הרצה שעובדות ממכונה נקייה
   - פסקה שמנמקת את עיצוב הכלים שלכם — למה הסעיפים מפוצלים ככה, מה `search` מחזיר ולמה

   - ממוצע קריאות הכלים לשאלה

3. **הדגמה** — סרטון של 3 דקות, או הדגמה חיה בכיתה

ההשוואה בסעיף 2 עולה לכם שעה והיא המשפט הכי בעל ערך בכל ההגשה. הקורפוס הזה נכנס כולו לחלון הקשר אחד — כדאי שתדעו מה קניתם בזה שבניתם שליפה.

## מפתחות API ותקציב

**מפתח ה-API של הפרויקט מגיע ממני, עם תקרת הוצאה לכל צוות.**

שלוש נקודות חשובות:

1. **המפתח הזה הוא לאפליקציה שלכם — לא ל-Claude Code.** אל תגדירו אותו כ-`ANTHROPIC_API_KEY` גלובלי במערכת. Claude Code שורף סדר גודל יותר טוקנים מהצ'אטבוט שתבנו, והוא ירוקן את התקרה תוך שעות. ל-Claude Code תשתמשו במנוי שלכם.

2. **לא מעלים לאוויר.** אפליקציית Streamlit ציבורית עם המפתח שלי ובלי אימות היא דרך לאבד כסף אמיתי בלילה אחד. הפרויקט רץ מקומית: `streamlit run`, המפתח ב-`.env`, ו-`.env` ב-`.gitignore`.

3. **תעקבו אחרי מה שאתם שורפים.** התקרה מגינה עליי, לא עליכם — צוות שמגיע אליה ביום השני נשאר בלי מפתח.

מעבר לזה הפרויקט לא עולה כסף. כל הסטאק חינמי, אין תשתית לשלם עליה, ואין ספק שני.
